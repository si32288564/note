# DNS・DHCP・RADIUS ランサムウェア対策バックアップ基盤

## 1. 目的

DNS・DHCP・RADIUSの各サーバーがランサムウェアなどによって完全に破壊された場合でも、必要なデータをAWSから取得し、ゼロから再構築できるバックアップ基盤を構築する。

### 基本要件

- オンプレミスとは独立したAWS上にバックアップを保管する。
- 過去90日間の任意の日付（1日単位）へ復元できること。
- DNS・DHCP・RADIUSはサービス単位で独立して管理する。
- RADIUS約100台など、複数サーバーを個別に識別・復元できること。
- ランサムウェアによるバックアップの改変・削除を防止する。
- 古い世代は低価格なS3ストレージクラスに移行し、コストを最適化する。

## 2. システム構成

### オンプレミス

新規物理サーバーを1台導入し、KVM上に2台のVMを構築する。

| コンポーネント | 役割 |
|---|---|
| 物理サーバー | KVM仮想化基盤 |
| rsync VM | 各サーバーからバックアップを収集・保管し、NFSで公開 |
| DataSync Agent VM | NFSを参照してAWSへバックアップを転送 |

DataSync AgentはAWS提供の仮想アプライアンスを使用する。

### AWS

| コンポーネント | 用途 |
|---|---|
| AWS DataSync | オンプレミスからS3への転送 |
| Amazon S3 | バックアップデータ保管 |
| S3 Versioning | 過去バージョン保持 |
| S3 Object Lock | バックアップの改変・削除防止 |
| S3 Lifecycle | 古い世代の低価格クラス移行・期限切れ削除 |
| VPC Interface Endpoint | Direct Connect経由のDataSync接続 |
| IAM | サービス別アクセス権限管理 |
| CloudWatch | 転送ログ・監視 |
| EventBridge / SNS | 異常検知・通知 |

### ネットワーク

- 既存AWS Direct Connectを利用する。
- 接続方式：Private VIF → VGW
- 既存VPCを利用する想定。
- DataSync用Interface Endpointを構築する。
- Direct Connect Gatewayの要否と既存経路の適合性は別途確認する。
- AWS側にEC2やNAT Gatewayを新規構築する想定はない。

## 3. バックアップ管理方式

### サービス別管理

- DNS
- DHCP
- RADIUS

各サービスでDataSyncタスク、S3バケット、バックアップ世代、監視を分離する。

### サーバー別管理

RADIUSは約100台存在するため、サーバー単位でデータと取得結果を管理する。

管理階層：

`サービス → サーバー → バックアップ世代`

各サーバーについて、バックアップ取得日時、成功・失敗、整合性などを記録する。

DataSync Agentは1台を共用し、DataSyncタスクはサービス単位で3個を基本とする。

### 世代管理

- バックアップ頻度：1日1回（仮定）
- 保持期間：90日
- 復元粒度：日付・サービス・サーバー単位
- 日次の復旧ポイントを明示的に管理する。
- 取得に失敗したサーバーは、その日の復旧ポイントで識別できるようにする。
- 整合性のある復旧ポイントとマニフェストを保存する。

※ S3 Versioningだけでは日付単位の一貫した復旧ポイントは自動的に保証されないため、世代確定・復旧管理の仕組みが必要。

## 4. データ容量

### 現時点の推定

| 対象 | 容量 |
|---|---:|
| DNS | 50GB |
| DHCP | 50GB |
| RADIUS | 300GB（仮定） |
| 合計 | 約400GB |

実際のデータ量は未確定。

### 見積もり条件

- 1世代あたり1TBを想定。
- オンプレミスのバックアップ用ディスクは2TB程度を初期目安とする。
- RAID構成、必要実効容量、ローカル保持世代数は別途設計する。

AWS側は予算確保のため、最大90日分のフルバックアップを保存する上限ケースを見積もる。

- 1TB × 90世代 = 90TB
- 実際には差分同期・増分管理による容量削減を検討する。

## 5. S3保管ポリシー

| 項目 | 方針 |
|---|---|
| 保存期間 | 90日 |
| 直近0〜30日 | S3 Standard |
| 31〜90日 | S3 Standard-IA |
| Versioning | 有効 |
| Object Lock | Compliance modeを基本案 |
| Object Lock保持期間 | 90日 |
| Lifecycle | 保護期間満了後に削除 |

90日間の各日付の復旧ポイントを維持することを優先する。

Object Lockによる保護期間、バージョン管理、Lifecycleの削除条件は整合させる。

また、バックアップ書き込み権限と保護設定の管理権限を分離する。

## 6. AWS見積もり条件

| 項目 | 数量・条件 |
|---|---|
| リージョン | 東京（ap-northeast-1） |
| DataSync Agent | オンプレミスに1台 |
| DataSyncタスク | 3個 |
| DataSyncモード | Basic modeを基本 |
| S3バケット | 3個 |
| S3 Standard | 30TB |
| S3 Standard-IA | 60TB |
| DataSync転送量 | 30TB/月（上限ケース） |
| VPC Interface Endpoint | 1AZ、24時間稼働 |
| IAM | サービス別 |
| CloudWatch | ログ・アラーム |
| EventBridge / SNS | 障害通知 |
| Direct Connect | 既存回線を流用 |
| KMS | 必要に応じて追加 |

### AWS利用料金の参考概算

上限ケース（日次フルバックアップ）：

- S3 Standard：約$750/月
- S3 Standard-IA：約$828/月
- DataSync：約$375/月
- 合計：約$1,953/月＋周辺費用

※ 参考単価による概算。東京リージョンの正式単価による見積もりが必要。

※ S3 APIリクエスト、Lifecycle移行、PrivateLink、CloudWatch、復旧時の転送料金等は別途。

※ 差分保存方式を採用できれば大幅な費用削減が見込めるが、復元可能性の検証が必要。

## 7. 物理サーバー見積もり条件

| 項目 | 初期想定 |
|---|---|
| CPU | 12〜16コア程度 |
| メモリ | 64〜128GiB |
| 仮想化 | Linux KVM |
| VM数 | 2台 |
| DataSync Agent VM | 8 vCPU / 32GiB RAM / 80GB |
| rsync VM | 2〜4 vCPU / 8〜16GiB RAM |
| バックアップストレージ | 実効2TB程度を初期目安 |
| OSストレージ | SSD RAID1 |
| ネットワーク | 1GbE以上 |

上記は初期見積もり用の目安であり、実際のファイル数、転送量、ローカル保持期間に応じて調整する。

## 8. ランサムウェア対策上の要件

- S3 Object Lockによる改変不能なバックアップ保持
- バックアップ対象サーバーから過去世代を削除できない権限設計
- DataSyncに必要最小限のS3アクセス権限を付与
- 可能ならバックアップ専用AWSアカウントへ分離
- バックアップ取得・転送結果の監視
- 過去の正常な復旧ポイントを選択できること
- 指定日時のデータからサービスを再構築できることを定期的に検証

## 10. 現時点の方針

**まずは最大90TBのS3保管容量と30TB/月のDataSync転送量を用いて、余裕を持ったAWS見積もりを取得する。**

同時に、オンプレミスの物理サーバーを1台新規導入し、rsync VMとDataSync Agent VMを分離する構成でハードウェア見積もりを取得する。

詳細なデータ量調査や増分バックアップ方式の検討は、概算予算の取得後に実施する。

最終的には、90日間の任意の日付への復旧可能性を維持しながら、S3の保存容量とDataSync転送量を最適化する。
